# 診所內部預約系統｜產品需求文件（PRD）

版本：2026-11-13  
搭配文件：《診所預約系統_Claude_Code開發規格.md》（以下稱「規格」）。本 PRD 說明做什麼、為什麼、怎麼驗收；欄位、資料表、API 細節以規格為準。兩者衝突時，以本 PRD 第 6 節「實作預設決策」與規格中較新的內容為準。

---

## 1. 一句話

業務用手機或電腦，在四步驟內幫客戶約到一個不會撞期、符合醫師班表的一小時時段，並能自己管理名下的預約；店長在後台掌握全院每日預約、處理例外，並在業務異動時收到通知。

## 2. 為什麼要做

**現況問題**

- 預約靠口頭、訊息或紙本協調，同一時段容易被兩個業務重複約走。
- 業務不清楚哪天哪個時段有醫師，常約到醫師不在的時間，事後才要改。
- 客戶要改時間時，業務得先問店長，店長變成人工客服。
- 醫師臨時請假時，沒有辦法快速知道哪些客戶受影響、該由誰聯絡。
- 沒有紀錄可以回頭查是誰改了什麼、客人有沒有到。

**做完之後**

- 系統保證一個時段只會被約一次（除非店長刻意加開），醫師班表自動把關。
- 業務自己查得到、改得動自己的預約，店長只處理例外。
- 班表一改，受影響的預約自動標紅，交給對應業務處理。
- 所有異動都有紀錄，店長透過 email 掌握重要變動。

## 3. 使用者

| 角色 | 人數（目前） | 使用情境 | 主要裝置 |
| --- | --- | --- | --- |
| 業務 | 數位（名單待補） | 在外或在診所幫客戶預約、回答客戶「我約幾點」、改期取消 | 手機為主，電腦為輔 |
| 店長 | 1 | 每天看總覽、加開、標記到診、處理衝突、維護班表與設定 | 電腦為主 |
| 代理店長 | 1（店長請假時才啟用） | 店長不在時處理預約 | 電腦或手機 |

## 4. 使用者故事

### 故事 1：業務快速建立預約

> 身為業務，我想在手機上幾步就幫客戶約好時間，這樣客戶在我面前就能確認，不用回頭再聯絡。

驗收標準：

- 四步驟：客戶資料 → 預約服務 → 預約時間 → 備註與確認；可隨時上一步，資料不消失。
- 負責業務自動是我，不需要選。
- 只看得到「現在起 1 小時後」到「今天＋60 天」之間、仍有空位、且符合醫師需求的時段。
- 選「需要醫師」後，只出現該醫師有班的時段，並顯示安排的醫師姓名。
- 送出後顯示預約編號與摘要；網路斷掉重送不會變成兩筆。
- 手機單手可完成，按鈕不被鍵盤遮住。

### 故事 2：同時段搶位與加開

> 身為業務，當我想約的時段已經被別人約走，我想立刻知道並知道下一步怎麼做；身為店長，遇到特殊情況我想能硬塞一筆。

驗收標準：

- 兩個業務同時搶同一時段，只有一人成功；另一人看到「此時段已被預約，如需同時段預約請訊息店長」，其他已填資料保留。
- 店長可在已滿的時段加開，筆數不限，原因必填；後台顯示「超額」。
- 加開時若同時段已有另一筆需要醫師，跳出警告，確認後仍可加開。
- 業務永遠無法自己約到已滿的時段。

### 故事 3：業務管理自己的預約

> 身為業務，客戶打來問時間或要改期時，我想自己查、自己改，不用每次找店長。

驗收標準：

- 「我的預約」只列出負責業務是我的今天與未來預約，看不到別人的。
- 距開始 4 小時以前：可改期、改項目、改醫師需求、取消。
- 距開始 4 小時內：只能改姓名、電話、備註、人數；其他按鈕停用並說明「請聯絡店長」。
- 改期到已滿時段失敗時，原預約完全不變。
- 改到別的時段後，若原本是超額預約，提示「改期後無法改回原時段」。
- 我改了或取消，店長會收到通知（依通知設定）。
- 我用網址猜別人的預約編號，系統回「找不到」。

### 故事 4：醫師請假的衝突處理

> 身為店長，醫師臨時請假時，我想系統告訴我哪些預約受影響，並讓各業務自己去聯絡客戶。

驗收標準：

- 店長登記請假前，系統先列出受影響的預約；確認後才儲存。
- 受影響預約在後台與各業務「我的預約」標示衝突；業務頁面最上方紅字顯示「有 N 筆預約需要處理」。
- 業務可改期、取消、或改成僅護理師，且不受 4 小時限制。
- 店長可標記「保留，已與客戶確認」（原因必填），紅字消失。
- 醫師說不請假了、班表改回後，衝突自動解除。
- 系統不會自動取消任何預約。

### 故事 5：店長每日總覽與到診紀錄

> 身為店長，我想一打開就看到今天每個時段的狀況，並記錄客人有沒有來。

驗收標準：

- 預設今天，可切換日期；每個時段清楚顯示空檔、已預約、超額、封鎖、休診、衝突；週日顯示休診。
- 點開預約可看電話、醫師、備註、超額原因、衝突紀錄。
- 時段開始後可標記「已到診」或「未到」；之後可依業務、狀態篩選統計。
- 兩人同時改同一筆時，後送出者看到「已被更新，請重新載入」，不會互相覆蓋。

### 故事 6：店長請假時的代理

> 身為店長，我請假時希望有人能處理預約，但不希望他能動帳號和班表。

驗收標準：

- 代理店長帳號平常停用、無法登入；店長在後台一鍵啟用／停用。
- 啟用後可看全院預約、新增、加開、改期、取消、標記到診與保留；進不了設定、帳號、班表與操作紀錄。
- 代理店長每個動作，店長立即收到 email。
- 停用當下，已登入的代理店長立即被登出。

### 故事 7：店長掌握異動但不被信件淹沒

> 身為店長，我想知道業務改了什麼，但不想一天收二十封信。

驗收標準：

- 後台通知鈴列出所有事件，可標已讀。
- 設定中心可對每種事件選「即時」「日報」「不寄」；預設：取消、4 小時內修改、代理店長操作、重複電話為即時，一般修改進日報。
- 日報每天 21:00 寄一封，沒有事件就不寄。
- 收件地址可設多個、隨時修改。
- 寄信失敗不影響預約成功，系統會重試並記錄。

### 故事 8：防止重複約與搶客

> 身為店長，我想知道是不是有兩個業務在約同一位客戶。

驗收標準：

- 業務送出時，若同一支電話（不論格式、含 +886、分機）已有未來預約，跳出「此電話已有預約，確定要再建立一筆嗎？」。
- 警告不透露是誰約的、約在何時。
- 業務確認後仍可送出，店長收到「重複電話預約」通知，內容含兩筆資訊。

### 故事 9：店長維護設定，不用找工程師

> 身為店長，醫師班表、預約項目、業務名單有變動時，我想自己在後台改好，前台立刻生效。

驗收標準：

- 可管理業務名單、帳號、預約項目、醫師、班表、營業時間、休診／封鎖／請假、最遠可約天數、通知設定。
- 改完前台立即讀到新資料，不需重新部署。
- 被歷史預約用過的項目只能停用不能刪除，歷史預約照常顯示原名稱。
- 業務離職：名下還有未來預約時無法停用，系統列出這些預約，預設可一次全轉給另一位業務，也可逐筆改。
- 無法停用最後一位店長。

## 5. 成功指標

**上線驗收（必須全數通過）**

- 規格第 10 節驗收清單 27 項全部通過，且有可重複執行的自動測試覆蓋：權限、並行搶位、超額加開、1 小時／4 小時規則、改期回滾、衝突計算、台北跨日判斷。
- 在手機與桌面各實際跑過一次完整預約流程、我的預約修改流程、錯誤狀態。
- 正式環境沒有任何預設密碼；repo 中沒有任何秘密。

**上線後一個月觀察**

- 重複預約（非店長加開）發生 0 次。
- 約到醫師不在時段的預約 0 筆（班表異動造成的衝突除外）。
- 業務新建一筆預約的中位時間在 1 分鐘以內。
- 店長每天收到的即時 email 不超過 5 封（超過則調整通知設定）。
- 業務因「查不到自己的預約」來找店長的次數明顯下降（由店長主觀回報）。

## 6. 實作預設決策（拷問與決策圖後補定，可再調整）

以下為使用者尚未逐項確認、由本 PRD 先行採用的預設；開發 AI 請照此實作，並在交付說明中列為「可調整決策」。

| 主題 | 預設 | 理由 |
| --- | --- | --- |
| Supabase 方案 | Pro（每日自動備份、不會因閒置暫停） | 規格要求備份；免費版需另做備份機制。若維護者決定先用免費版，改以 GitHub Actions 每日 pg_dump 作為備份 |
| 登入方式 | 自建 session（session 存資料庫、HttpOnly Cookie） | 登入帳號可非 email；停用帳號可立即刪除 session |
| 日報寄送時間 | 固定 21:00（台北），設定中心先不開放調整 | 避免需要每小時執行的排程；日後需要再改 |
| 業務離職轉出 | 預設一次全轉給同一人，可逐筆改 | 最常見情境最快完成 |
| 時區 | 所有日期時間判斷明確以 Asia/Taipei 計算，不依賴主機時區 | Vercel 主機為 UTC |
| 鎖位 | 使用交易層級鎖（pg_advisory_xact_lock 或 slot_locks 表 FOR UPDATE） | Supabase 連線池為 transaction 模式，session 層級鎖不可靠 |
| 電話正規化 | 移除空格、橫線、括號、分機；`+886` 開頭轉為 `0` | 同一支電話不同寫法要能比對 |
| 4 小時外改成需醫師 | 必須重查該時段醫師班表，不符合則拒絕 | 避免繞過班表 |
| 超額預約改期 | 介面提示「改期後無法改回原時段，如需保留請聯絡店長」 | 避免業務誤失加開位置 |
| 我的預約範圍 | 只顯示今天與未來 | 過去預約交由店長後台查詢 |

> 註：規格 7.2「通知設定」中的「日報寄送時間」與 5.1 的「每日日報寄送時間 21:00」依本表改為固定值，不在設定中心顯示。

## 7. 範圍外（本版不做）

- 付款、病歷、處方、藥品。
- 寄給客戶的任何通知（簡訊、LINE、email）。
- 業務收 email 通知。
- 客戶自行線上預約。
- 「換醫師」專用介面（同時段目前只有一位醫師；資料結構已支援，未來排班後選單自動出現）。
- 跨日營業、半點時段、非一小時的服務。
- 報表匯出與統計圖表（已到診／未到資料先保存，報表下一版再做）。
- 個資合規文件與資料落地要求。

## 8. 開發順序（依決策依賴）

1. 基礎設施：Supabase、Vercel、環境變數、migration、初始化資料、首位店長建立。
2. 登入與角色：session、登入限制、三種角色、業務帳號綁定業務名單。
3. 時段與容量：可約時段計算、交易鎖位、1 小時規則、最遠天數、冪等送出。
4. 前台四步驟預約流程（含手機版）。
5. 防呆：重複電話警告。
6. 我的預約：查看、4 小時規則修改／取消、並行控制。
7. 店長後台：每日總覽、新增、超額加開、改期、取消、改負責業務、標記到診／未到。
8. 設定中心：業務、帳號、項目、醫師、班表、營業、休診／封鎖、最遠天數。
9. 班表衝突：異動前影響預覽、異動後重算、紅字、保留標記、自動解除。
10. 帳號生命週期：業務停用轉出、代理店長啟停、最後店長保護。
11. 通知：後台通知清單、即時 email、21:00 日報、失敗重試。
12. 測試與交付文件：自動測試、手機／桌面實測、部署與備份還原說明。

每完成一個階段，應可實際部署到 Vercel 並操作驗證，再進入下一階段。

## 9. 待補資料（不阻擋開發）

- 週五醫師姓名、真實業務名單、代理人人選。
- 通知收件 email、寄信網域 DNS 設定。
- 診所正式名稱、Logo、蒲原健康診所網址或截圖。
- Vercel、Supabase、Resend 帳號。
