# 診所內部預約與後台管理系統｜Claude Code 開發規格

版本：2026-11-13 拷問修訂版（取代 2026-11-13 整合版）  
用途：將本檔交給 Claude Code，作為功能、資料庫、權限與 UI／UX 的統一實作依據。這是需求文件，並非已完成的網站。

> 本版相較整合版的主要變更：確定部署架構（GitHub＋Vercel＋Supabase）；業務一律個人帳號，取消代填；新增業務「我的預約」可自行修改／取消；新增 1 小時／4 小時時間規則；店長可強制加開超額預約；新增「代理店長」角色；預約狀態增為四種；班表衝突交由業務處理；新增最遠可約天數、重複電話警告與 email 通知。

## 1. 給開發 AI 的指令

請依本文件實作可運作的診所內部預約系統。需有真實後端、資料庫、登入權限及持久保存，不可用假資料或 localStorage 代替正式功能。所有介面使用繁體中文，時間以 Asia/Taipei 計算。

**已確定的部署架構：**

- 程式碼：GitHub private repo。
- 網站：Vercel，連結 GitHub 自動部署。
- 資料庫：Supabase PostgreSQL，區域選東京（ap-northeast-1）。
- 寄信：Resend（或等效交易型 email 服務），建議綁診所網域。
- 排程（每日 email 日報）：Vercel Cron 或 Supabase 排程。
- 建議框架：Next.js（App Router）＋ TypeScript＋ Supabase PostgreSQL。登入驗證可自建或使用 Supabase Auth，但必須滿足第 6 節的所有要求（登入帳號非 email 亦可、停用即撤銷 session、登入嘗試限制）。選擇後簡述理由再開始開發。

維護者只有一人（非專職工程師），請選擇主流、文件完整、易於日後修改的做法，避免冷門套件與過度抽象。所有秘密（資料庫連線、寄信金鑰、session 金鑰）放環境變數，不寫入程式碼或 repo。

採「循序漸進分步表單」，前台是一條完整預約流程，不必同時顯示所有欄位。完成後提供啟動、環境設定、資料庫 migration、初始化與測試方式。不要將未實作或未驗證的功能說成已完成。

## 2. 系統目標及範圍

業務以個人帳號替自己的客戶預約，並管理自己名下的預約；店長查看並管理全院預約。前台簡單、直覺、填寫順暢；後台提供每日總覽與設定編輯。業務看不到其他業務的客戶。

- 一般情況下全院同一日期、同一時段只允許一筆占用中的預約，醫師與護理師服務共用容量；只有店長／代理店長可強制加開超額預約（見 5.4）。
- 一筆可包含多人，但仍占一小時；人數只作紀錄，不增加可接受的預約筆數。
- 所有使用者必須以個人帳號密碼登入，不開放匿名預約。
- 系統內部 email 通知（寄給店長設定的收件地址）納入本版範圍。
- 不納入付款、病歷、藥品處方、簡訊、LINE 通知及寄給客戶的任何通知。
- 個資合規（如資料落地、同意書）本版暫不處理，但須做到：repo 為 private、秘密不入程式碼、全站 HTTPS、權限於伺服器端檢查。

## 3. 前台使用者體驗（業務）

### 3.1 分步流程

頂端呈現簡潔進度，例如「步驟 1／4」。每一步只顯示少量相關欄位；明確提供上一步、下一步。欄位填完不突然自動跳頁，以使用者按下一步為準。返回前一步保留資料。

| 步驟 | 標題 | 欄位與動作 |
| --- | --- | --- |
| 1 | 客戶資料 | 姓名、電話（負責業務自動為登入者，以小字顯示「負責業務：○○○」，不可修改） |
| 2 | 預約服務 | 項目、人數、是否需醫師 |
| 3 | 預約時間 | 先選日期，再選符合條件的時段；旁邊提供精簡班表提示 |
| 4 | 備註與確認 | 希望指定醫師、特殊需求備註；下方摘要確認後正式送出 |

摘要需列出負責業務、客戶姓名與電話、項目、人數、服務方式、日期、時段、實際安排醫師及備註，並提供返回修改。成功頁顯示本次預約編號、摘要、「建立下一筆預約」與「前往我的預約」。只有伺服器成功保存後才顯示預約成功。

### 3.2 欄位規格

| 欄位 | 必填 | 元件與規則 |
| --- | --- | --- |
| 負責業務 | — | 不顯示選單；伺服器以登入帳號綁定的業務名單決定，不接受前端傳值 |
| 預約姓名 | 是 | 文字，去除首尾空白 |
| 聯絡電話 | 是 | 電話輸入框，以字串保存原輸入，保留開頭 0，支援手機、市話與分機 |
| 預約項目 | 是 | 下拉選單，來源為後台啟用項目 |
| 預約人數 | 是 | 正整數，預設 1，不接受 0、負數或小數 |
| 是否需要醫師 | 是 | 明顯的兩個選項：「是，需安排醫師」「否，僅由護理師服務」 |
| 預約日期 | 是 | 日期元件，不使用自由文字；只能選今天到「今天＋最遠可約天數」之間；停用過去、休診或無可約時段的日期；顯示「可預約至 ○月○日」 |
| 預約時段 | 是 | 下拉選單；顯示起訖時間；額滿或距開始不足 1 小時的時段停用 |
| 希望指定的醫師 | 否 | 文字備註，提示「希望安排，不代表已確認」 |
| 特殊需求／照護備註 | 否 | 多行文字，提示例如怕痛、不好打針等 |

預約項目初始選項：一般健保看診、一般自費看診、療程諮詢、例行保養與療程、點滴／針劑、疫苗、其他。所有項目名稱、順序及啟用狀態可於後台管理。

### 3.3 互動與錯誤狀態

- 下一步檢查當前欄位，錯誤直接顯示於欄位旁並將焦點移到第一個錯誤。
- 更改日期或服務方式後重新載入可約時段；僅清除已失效的選擇，其他內容保留。
- 選需醫師時顯示符合班表的實際安排醫師；指定醫師備註不得覆寫班表。
- 無可約時段時顯示「此日期目前無可預約時段，請選擇其他日期」。
- 送出時若時段已被占用（含並行搶位），顯示「此時段已被預約，如需同時段預約請訊息店長」，保留其他已填資料並更新時段選項。
- **重複電話警告**：送出前，若同一支電話（正規化後比對，見 5.6）在未來已有有效預約，顯示「此電話已有預約，確定要再建立一筆嗎？」，不顯示既有預約的業務、日期或時段；業務確認後仍可送出，並觸發「重複電話預約」通知。
- 送出中停用重複送出；後端仍需具備冪等控制。
- 網路或驗證失敗保留已填資料；重試不得多建立一筆。
- 不將姓名、電話與照護備註放入網址或長期保存在瀏覽器 localStorage。
- 支援手機、平板、電腦；手機採單欄，按鈕不得遮住最後欄位或被鍵盤擋住。
- 提供清楚標籤、鍵盤操作、可見焦點及足夠對比，不只以顏色表示狀態。

### 3.4 我的預約

業務登入後可從導覽進入「我的預約」。

- 只列出**負責業務為自己**的預約（salesperson_id 等於登入帳號綁定的業務），預設顯示今天及未來的預約，依日期時間排序。
- 頁面最上方若有衝突預約，以紅字（並附圖示與文字，不只靠顏色）顯示「有 N 筆預約需要處理」，點擊可篩出這些預約；每筆標示衝突原因，例如「醫師請假，需改期」。
- 可查看自己預約的完整內容（含電話與照護備註）。
- 可修改與取消，規則見 5.3；不符合時間規則的操作按鈕停用，並以文字說明原因，例如「距開始不足 4 小時，如需更改請聯絡店長」。
- 業務不可修改負責業務；要轉給其他業務需由店長處理。
- 超額預約（見 5.4）對該業務可見，可依一般規則修改；若改到其他時段，只能改到空的時段。
- 修改採版本號並行控制；若同時有人改過，顯示「此預約已被更新，請重新載入後再修改」。
- 業務每次修改或取消後，依通知設定觸發對應通知（見第 7.4 節）。

## 4. 視覺方向

奶茶色、米白背景、深咖啡色文字，留白充足、裝飾克制、簡單且有質感。避免前台出現大型表格、密集資訊、過多卡片及複雜導航。主動作清楚，次要資訊以輔助文字或可展開區呈現。

將顏色、字體、間距、圓角等集中為設計變數，便於後續調整。使用者指定參考「蒲原健康診所」官網，但目前尚無經確認的網址或截圖；本版僅採奶茶色方向，不宣稱已比照官網。取得參考素材後再調整視覺，不阻擋功能實作。

## 5. 營業、班表及預約規則

### 5.1 初始設定

| 類別 | 星期 | 時間 | 最後可約時段 |
| --- | --- | --- | --- |
| 全院／僅護理師服務 | 週一至週六 | 10:00–19:00，中午不休息 | 18:00–19:00 |
| 廖醫師 | 週二 | 13:00–19:00 | 18:00–19:00 |
| 嚴醫師 | 週四 | 13:00–19:00 | 18:00–19:00 |
| 週五醫師（姓名待補） | 週五 | 10:00–17:00 | 16:00–17:00 |
| 全院休診 | 週日 | 不開放 | — |

每日九個一小時時段：10:00–11:00、11:00–12:00、12:00–13:00、13:00–14:00、14:00–15:00、15:00–16:00、16:00–17:00、17:00–18:00、18:00–19:00。不得產生 19:00–20:00。

週五醫師以待補名稱初始化，不捏造姓名。初始資料可從後台修改，不把班表寫死在前端。

系統設定初始值：最遠可約天數 60 天；每日日報寄送時間 21:00；通知收件地址空白（由店長填入）。

### 5.2 可約時段算法（業務新建預約）

1. 以台北時間取得日期與星期，依後台營業設定產生整點起算的一小時候選時段。
2. 排除超過「今天＋最遠可約天數」的日期。
3. 排除過去、已開始，以及**距開始不足 1 小時**的時段。
4. 排除全院休診與封鎖。
5. 排除已有占用中預約的時段（占用中定義見 5.4）。
6. 僅護理師服務到此即可；需醫師時再確認完整一小時落在啟用醫師的有效班表內，且該醫師未請假或被封鎖。
7. 需醫師時必須保存實際安排的醫師。目前同一時段最多一位醫師，系統自動帶入；若未來班表使同一時段有多位醫師，顯示符合條件的醫師選單供選擇。不可依自由文字猜測安排。不另做「換醫師」專用介面。
8. 個別醫師請假只影響該醫師；全院封鎖影響所有服務。封鎖優先於開放。
9. 前端選項僅供引導，送出時由後端重新計算與驗證。

目前依初始班表，週一、週三、週六不能建立需醫師預約。班表改動後應依資料動態計算，不把此限制寫死。

### 5.3 業務的時間規則

以下「距開始」皆以台北時間的實際時間計算（不扣除休診時間）。

| 操作 | 規則 |
| --- | --- |
| 新建預約 | 時段開始前至少 1 小時 |
| 改期（改日期或時段） | 原時段開始前至少 4 小時；新時段需開始前至少 1 小時，且為空的時段、符合班表 |
| 改項目、改醫師需求 | 原時段開始前至少 4 小時，並重新驗證班表 |
| 取消 | 原時段開始前至少 4 小時 |
| 改姓名、電話、備註、人數 | 時段開始前皆可改；若在 4 小時內修改，觸發「4 小時內修改」通知 |
| 改負責業務 | 業務不可，僅店長 |
| 已開始或已過去的預約 | 業務不可做任何修改 |

**衝突預約例外**：被標記為衝突（見 5.5）的預約，改期、取消、將「需要醫師」改為否（改成僅護理師服務），不受 4 小時限制；但仍不可修改已開始的時段，改期的新時段仍須遵守 1 小時與空時段規則。

店長與代理店長不受 1 小時／4 小時限制，但不可新建或改期到已開始的時段。

### 5.4 容量、超額加開、狀態

**預約狀態**：

| 狀態 | 意義 | 是否占用時段 | 誰可設定 |
| --- | --- | --- | --- |
| active（有效） | 已預約 | 是 | 建立時預設 |
| completed（已到診） | 客戶已到 | 是 | 店長、代理店長；時段開始後才可標記 |
| no_show（未到） | 客戶未到 | 是 | 店長、代理店長；時段開始後才可標記 |
| cancelled（取消） | 已取消，保留紀錄 | 否 | 業務（依 5.3）、店長、代理店長 |

已到診與未到之間可由店長互相更正，並記錄稽核。

**一般容量**：

- 業務新建或改期時，目標時段必須沒有任何占用中的預約。
- 不可只先查詢再新增。以「時段鎖」實作：在同一交易中鎖定該日期＋開始時間（例如對 slot 鎖定列 `SELECT … FOR UPDATE`，或 PostgreSQL advisory lock），計算占用筆數後再決定寫入。並行請求最多一筆成功，其餘回應「此時段已被預約，如需同時段預約請訊息店長」（HTTP 409）。
- 所有預約固定一小時，整點開始；不得接受任意半點時段。

**超額加開（僅店長、代理店長）**：

- 可在已有占用預約的時段再加開，筆數不設上限。
- 加開時必填原因（例如「同一家人分兩組」），原因寫入預約與操作紀錄。
- 加開的預約標記為超額（is_overbooked = true）；後台在同一時段有兩筆以上占用預約時顯示「超額」。
- 若加開預約需要醫師，而同時段已有其他需要醫師的占用預約，先跳警告「同一時段醫師已有其他預約」，確認後仍可加開。
- 加開時須指定負責業務；該業務可在「我的預約」看到並依 5.3 修改。業務若維持同一時段，修改基本欄位不影響超額狀態；若改到其他時段，依一般容量規則，只能改到空的時段。
- 超額加開仍須符合營業時間、休診、封鎖與醫師班表（需醫師時）；不可用加開繞過休診。

**取消與改期**：

- 取消將狀態改為 cancelled 並保留紀錄，在同一交易釋出容量。
- 修改與改期重新檢查全部規則；新時段取得失敗時整筆回滾，原預約保持不變。

### 5.5 班表異動與衝突處理

- 班表、醫師請假、營業時間、休診或封鎖異動時，儲存前先列出受影響的未來占用預約，店長確認後儲存。
- 儲存後由伺服器重新計算所有未來 active 預約，對不再符合規則者標記衝突（記錄衝突原因，例如「醫師請假」「全院封鎖」「超出營業時間」）。不自動取消或刪除預約。
- 衝突預約在店長的每日總覽與業務的「我的預約」中標示；由各負責業務聯絡自己的客戶處理。
- 衝突解除方式：
  1. 改期到符合規則的時段。
  2. 取消。
  3. 將「需要醫師」改為否（僅限衝突原因只與醫師有關時；時段仍須符合全院營業與封鎖規則）。
  4. 店長或代理店長標記「保留，已與客戶確認」，原因必填。此預約不再顯示衝突，但後台詳情保留紀錄。
- 班表再次異動時重新計算：原本衝突、現已符合規則的預約自動解除衝突；先前被標記「保留」的預約若再次因新的異動受影響，重新標記衝突。

### 5.6 重複電話比對

- 比對用電話：移除空格、橫線、括號，並移除分機部分（例如 `#123`、`轉123`、`ext 123`）後的純數字。原始輸入仍完整保存。
- 新建預約時，若同一比對用電話在今天以後已有 active 預約（不限業務），回傳警告，前端要求確認（見 3.3）。
- 警告回應不得包含既有預約的任何資訊（業務、日期、時段、姓名）。
- 確認送出後觸發「重複電話預約」通知；通知內容可包含兩筆預約的資訊（僅寄給店長）。

## 6. 帳號與權限

**角色**：

- **業務（sales）**：每人一個帳號，必須綁定一筆業務名單（一對一）。
- **店長（admin）**：全部權限。目前一位。
- **代理店長（deputy）**：只能處理預約。平常為停用狀態，店長請假前於後台啟用、回來後停用。固定由一位代理人保管密碼；代理人操作時，原因欄需寫上自己的姓名（介面提示）。

- 後台避免停用或降權最後一名啟用店長；代理店長不計入「最後店長」判斷。
- **業務停用**：若該業務名下仍有今天以後的 active 預約，系統列出這些預約並要求店長先轉給其他業務；全部轉出前不可停用。

## 7. 管理後台 UI 與可編輯設定

### 7.1 每日總覽

登入後預設顯示今日日期及九個時段（依營業設定動態變化），可切換日期；明確區分空檔、已預約、超額、封鎖、休診、衝突。週日顯示休診而非九個可用空檔。

預約摘要呈現時間、姓名、人數、項目、負責業務、醫師需求與狀態；點開詳情查看電話、實際醫師、備註、超額原因、衝突原因與處理紀錄，避免總覽資訊過密。提供依日期、業務、醫師需求、狀態及「僅顯示衝突」篩選；支援新增、超額加開、修改、改期、取消、改負責業務、標記已到診／未到、標記衝突保留。取消前顯示將取消的預約摘要供確認。

### 7.2 設定中心（僅店長）

所有下拉選單的業務資料及班表由後台管理，調整後前台直接讀取更新資料，不必改程式或重新部署。

| 設定項目 | 可操作內容 |
| --- | --- |
| 業務名單 | 新增、修改名稱、排序、啟用／停用；與業務帳號一對一綁定 |
| 預約項目 | 新增、修改、排序、啟用／停用 |
| 醫師名單 | 新增、修改姓名、啟用／停用 |
| 醫師班表 | 編輯星期、開始／結束時間、生效及截止日期 |
| 營業時間 | 編輯每週營業日及時間，初始週一至週六 10:00–19:00 |
| 休診／封鎖／醫師請假 | 指定日期或週期、起訖時間、全院或個別醫師、原因 |
| 使用者帳號 | 新增、改顯示名稱及登入帳號、角色、啟用／停用、重設密碼；代理店長提供明顯的「啟用／停用代理」開關 |
| 預約規則 | 最遠可約天數（預設 60） |
| 通知設定 | 收件 email 地址（可多個）、各事件寄送方式、日報寄送時間（見 7.4） |

日期及時段下拉選項由以上設定與即時容量計算，不讓店長直接編輯「額滿」狀態。固定權限角色、預約狀態與醫師需求布林值屬系統邏輯，不設任意文字選項。

已被歷史預約引用的業務、醫師、項目及帳號採停用而非硬刪除；未被引用的項目才可刪除。停用前提示受影響的未來預約。初始化只在首次建立缺少資料時執行，不覆蓋店長已修改的設定。

### 7.3 後台通知清單

- 店長與代理店長後台顯示通知鈴與未讀數；通知清單可標記已讀／未讀、可點進對應預約。
- 所有通知事件一律寫入後台通知清單（不受 email 設定影響）。

### 7.4 Email 通知

**事件與預設寄送方式**（每種事件在設定中心可各自改為「即時」「日報」或「不寄」）：

| 事件 | 預設 |
| --- | --- |
| 業務取消預約 | 即時 |
| 業務在 4 小時內修改姓名／電話／備註／人數 | 即時 |
| 代理店長的任何預約操作（新增、加開、修改、改期、取消、標記狀態、標記保留） | 即時 |
| 重複電話預約 | 即時 |
| 業務一般修改預約（4 小時前的任何修改） | 日報 |

- 即時信：事件發生後寄出，內容含事件類型、操作者、預約摘要與修改前後差異、後台連結。
- 日報：每天於設定時間（預設 21:00 台北時間）彙整前一次日報後的所有「日報」事件為一封信；無事件則不寄。
- 收件地址可多個，店長可隨時修改。
- 寄信失敗不得影響預約操作的成功；需記錄失敗並重試，後台通知照常產生。
- Email 內容不放密碼、憑證；照護備註只寫「已修改」不寫全文，詳細內容請登入後台查看。

## 8. 資料表與關聯

欄位命名可依框架調整，但以下語意、關聯、約束必須保留。所有外鍵在後端驗證存在與適用狀態。

| 資料表 | 主要欄位 |
| --- | --- |
| user_accounts | id、login_name（唯一）、password_hash、display_name、role（sales/admin/deputy）、active、created_at、updated_at |
| salespeople | id、display_name、active、sort_order、user_account_id（唯一；業務帳號必須綁定一筆）、created_at、updated_at |
| appointment_items | id、name、active、sort_order、created_at、updated_at |
| doctors | id、display_name、active、created_at、updated_at |
| doctor_shifts | id、doctor_id、weekday、start_time、end_time、effective_from、effective_to（可空）、active、created_at、updated_at |
| schedule_rules | id、rule_type（opening/block）、weekday（可空）、specific_date（可空）、start_time、end_time、scope（clinic/doctor）、doctor_id（可空）、effective_from、effective_to（可空）、reason、active |
| appointments | id、customer_name、phone、phone_normalized、appointment_date、start_time、end_time、item_id、party_size、requires_doctor、assigned_doctor_id（可空）、preferred_doctor_note、care_note、salesperson_id、status（active/completed/no_show/cancelled）、is_overbooked、overbook_reason（可空）、conflict_status（none/conflict/kept）、conflict_reason（可空）、conflict_kept_note（可空）、created_by、updated_by、created_at、updated_at、cancelled_at、version |
| slot_locks（或等效 advisory lock） | appointment_date、start_time（複合唯一），僅供交易內鎖定 |
| notifications | id、event_type、appointment_id（可空）、actor_user_id、payload（摘要與差異）、read_at（可空）、email_mode（instant/digest/none）、email_sent_at（可空）、email_error（可空）、created_at |
| system_settings | key、value（含最遠可約天數、日報時間、通知收件地址、各事件寄送方式）、updated_by、updated_at |
| audit_logs | id、entity_type、entity_id、actor_user_id、action、changed_fields、reason（可空）、created_at |

建議搭配 session 與冪等請求紀錄資料結構，依框架選擇實作。

關聯：一位業務可負責多筆預約；一個帳號可建立多筆預約；一個項目可對應多筆預約；一位醫師可有多筆班表與預約。audit_logs 以 entity_type/entity_id 記錄預約、班表、設定及帳號異動。

資料約束：

- party_size > 0；預約 end_time = start_time + 1 小時，且整點開始。
- requires_doctor = false 時 assigned_doctor_id 必須為空；為 true 時必須存在且符合班表（衝突狀態除外，衝突由 conflict_status 表示）。
- is_overbooked = true 時 overbook_reason 必填。
- conflict_status = kept 時 conflict_kept_note 必填。
- role = sales 的帳號必須恰有一筆綁定的 salespeople。
- weekday 統一 ISO 1–7（週一至週日）；整個程式採相同定義。
- schedule_rules 的 weekday 與 specific_date 必須擇一；scope=doctor 需 doctor_id，clinic 則不得帶 doctor_id。opening 先限全院營業設定，醫師開診由 doctor_shifts 管理。
- 結束時間大於開始時間、生效日不晚於截止日；本版不支援跨日營業。
- 預約日期及時段以台北本地日期／時間保存；稽核與通知時間戳使用帶時區時間或 UTC，顯示時轉台北時間。
- 修改採版本號或等效並行控制，避免兩人互相覆蓋異動（含業務與店長同時修改）。
- 操作紀錄由伺服器產生，限店長讀取；記錄必要異動與原因，不記錄密碼、雜湊、憑證或多餘敏感內容。

## 10. 驗收清單

1. 前台為四步驟流程，第一步為客戶姓名與電話，負責業務自動為登入者且無法更改；上一步保留已填資料。
2. 手機能完成全流程，文字清楚、按鈕可按、錯誤不清空其他欄位。
3. 初始週日不可預約；週一至週六每天九個時段，沒有 19:00–20:00。
4. 需醫師：週二與週四 13:00 前不可選，週五最後時段為 16:00–17:00。
5. 僅護理師服務可選營業時間內剩餘時段，不被無醫師出診日錯誤限制。
6. 改日期或醫師需求會更新時段並清除失效選擇。
7. 多人預約仍只占一個時段，完成後其他業務不能再訂同時段，並看到「如需同時段預約請訊息店長」。
8. 兩個並行請求搶同一時段最多一筆成功；重複送出相同請求不新增第二筆。
9. 業務無法新建距開始不足 1 小時的預約；無法選到超過最遠可約天數的日期。
10. 業務在「我的預約」只看到自己名下預約；距開始不足 4 小時無法改期、改項目、改醫師需求或取消，但可改姓名、電話、備註、人數並觸發即時通知。
11. 業務改期到已被占用時段失敗時，原預約保持不變。
12. 店長可在已占用時段超額加開（原因必填），兩筆皆需醫師時出現警告；業務仍無法約該時段。
13. 業務 B 可看到並修改店長替他加開的超額預約；改到其他時段時只能選空時段。
14. 取消後保留取消紀錄並釋出容量；已到診／未到只能在時段開始後由店長或代理店長標記。
15. 醫師請假後，受影響預約在後台與該業務「我的預約」標示衝突，紅字顯示筆數；衝突預約不受 4 小時限制可改期、取消或改成僅護理師；店長可標記保留；班表改回後衝突自動解除。
16. 同一電話（不同格式、含分機）已有未來預約時出現警告且不洩漏既有預約資訊；確認後可送出並通知店長。
17. 後端拒絕過去、非整點、非一小時、無班表、封鎖、偽造醫師或偽造負責業務的預約。
18. 業務直接呼叫管理 API 或猜測他人預約編號時一律拒絕（404），無法取得個資。
19. 代理店長平常停用無法登入；啟用後可處理預約但無法進入設定、帳號、班表與操作紀錄；停用後舊 session 立即失效；每次操作產生即時通知。
20. 業務名下仍有未來預約時無法停用該業務，需先轉出。
21. 後台新增、改名、排序、停用項目後，前台選項即時反映且歷史關聯保留。
22. 班表、休診、營業設定異動會先提示既有預約影響；不自動取消。
23. 通知設定可對每種事件選即時／日報／不寄；日報於設定時間寄出一封彙整信；寄信失敗不影響預約操作。
24. 密碼不可讀取、停用帳號無法繼續使用舊 session、最後店長受到保護。
25. 重新整理、重啟服務及換裝置後，資料仍持續保存。
26. 台北跨日邊界的今日、過去日期、1 小時與 4 小時判斷正確。
27. 同時編輯同一預約（業務與店長、或兩位店長）有衝突提示，不悄悄覆蓋資料。

針對權限、資料庫並行鎖位、超額加開、1 小時／4 小時規則、取消與改期交易、衝突計算、排程規則提供可重現測試；UI 至少實際驗證手機與桌面完整預約流程、「我的預約」修改流程及錯誤狀態。

## 12. 規格完成後補定的決策（2026-11-13，已實作於程式）

以下決策在本文件之後才定案，與前文衝突時以本節為準。

| 主題 | 決策 |
| --- | --- |
| 衝突保留 | 店長標記「保留」時記下當下衝突原因（`conflict_kept_reasons`）。重算時：原因都在其中 → 維持保留；出現新原因 → 重新標衝突；沒有原因 → 恢復正常 |
| 衝突原因 | 只有三種：`OUTSIDE_HOURS`（不在營業時間）、`BLOCKED`（全院封鎖）、`DOCTOR_UNAVAILABLE`（安排的醫師不在班、請假或停用）。超額與 1 小時規則不算衝突。`conflict_reason` 改為陣列 |
| 安排的醫師不在 | 即使同時段有別的醫師，仍算衝突，不自動換醫師；系統列出可替代醫師供店長參考 |
| 店長新建／加開 | 不受 1 小時規則；仍不可約已開始時段、非整點、營業外、全院封鎖、醫師不在班。同時段有兩位醫師時優先排有空的；店長指定忙碌醫師則照指定但需確認警告 |
| 占用狀態 | `active`、`completed`、`no_show` 占用時段；`cancelled` 不占用 |
