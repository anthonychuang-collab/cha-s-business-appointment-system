# PURE IN 預約系統｜部署與維運手冊

給負責上線與日常維護的人。依序做完「一、上線」即可正式使用；「二、日常維運」「三、備份」「四、還原」平常備查。

> 各服務的後台選單名稱可能改版，若與本文不同，以該服務當下的畫面為準；本文寫的是「要設定什麼」。

---

## 一、上線（第一次）

### 0. 事前準備

| 項目 | 說明 |
| --- | --- |
| Supabase 帳號 | 建議 **Pro** 方案：每日自動備份、不會因閒置被暫停 |
| Vercel 帳號 | **Pro** 方案：Vercel 的 Hobby 方案限非商業用途，診所屬商業使用 |
| Resend 帳號 | 寄通知信用 |
| 寄信網域 | 例如 `booking.診所網域`，需要能改 DNS 的人配合 |
| 一台電腦 | 執行建立資料表、建立第一位店長、備份。需安裝 Node.js 22 以上；備份另需 PostgreSQL 用戶端（`brew install postgresql@17 gnupg`） |
| 程式碼 | 本 GitHub repository |

上線前也請確認 `CLAUDE.md`「待使用者提供」的事項：週五醫師姓名、業務名單、代理人、通知收件 email、Logo 與照片使用權、週六營業時間。

### 1. 建立 Supabase 專案

1. 新增專案：區域選 **Northeast Asia (Tokyo)**，設定一組強資料庫密碼並存進密碼管理工具。
2. 開啟帳號的兩步驟驗證（MFA）；只邀請需要的人進 Supabase 後台。
3. 到專案的 **Connect**（或 Project Settings → Database）找連線字串，記下兩種：
   - **Transaction pooler**（port **6543**）：給 Vercel 上的程式用 → 之後填 `DATABASE_URL`
   - **Session pooler**（port **5432**）：給電腦上執行 migrate、建立店長、備份用
   - 兩者結尾都加上 `?sslmode=require`

本系統不使用 Supabase 的 API key、Auth 或 Storage；所有資料表都開啟 RLS 且不給任何權限，Supabase 公開的 REST API 讀寫不到。

### 2. 建立資料表與第一位店長（在電腦上執行）

```bash
git clone <repository> && cd <資料夾>
npm install
```

```bash
DATABASE_URL="<Session pooler 連線字串>" npm run db:migrate
```

```bash
DATABASE_URL="<Session pooler 連線字串>" npm run db:create-admin
```

- 第二個指令會詢問店長的登入帳號、顯示名稱、密碼（輸入時不顯示）。已有店長時會拒絕。
- **不要**對正式資料庫執行 `db:seed-dev` 或 `db:reset`（程式也會拒絕）。

### 3. 設定 Resend（寄信）

1. Domains → 新增寄信網域，依畫面把 SPF、DKIM（以及建議的 DMARC）記錄加到 DNS，等待驗證通過。
2. API Keys → 建立 key，權限選 **Sending access**、限定該網域。key 只會顯示一次。
3. 寄件者格式：`PURE IN 預約系統 <noreply@寄信網域>`

### 4. 建立 Vercel 專案

1. Add New → Project → 匯入 GitHub repository，Framework 會自動辨識為 Next.js，其他保持預設。
2. Settings → General → Node.js Version 選 **22.x**（`package.json` 也已標示）。
3. `vercel.json` 已設定：函式區域 **東京（hnd1，與 Supabase 同區）**、每日排程 UTC 13:00（台北 21:00）。
4. Settings → Environment Variables，**只勾 Production**：

| 變數 | 值 |
| --- | --- |
| `DATABASE_URL` | Supabase **Transaction pooler**（6543）連線字串，含 `?sslmode=require` |
| `DATABASE_POOL_MAX` | `5` |
| `RESEND_API_KEY` | Resend 的 key |
| `NOTIFY_FROM` | `PURE IN 預約系統 <noreply@寄信網域>` |
| `APP_BASE_URL` | 系統正式網址，例如 `https://booking.診所網域` |
| `CRON_SECRET` | 長亂數：`openssl rand -hex 32` 產生 |

> **重要：Preview（預覽）環境不要填正式的 `DATABASE_URL` 與 `RESEND_API_KEY`。** 每次推送分支都會產生預覽網站，若連到正式資料庫，測試操作會寫進正式資料並寄出真的通知信。需要預覽測試時，另建一個 Supabase 專案給 Preview 使用。也建議在 Settings → Deployment Protection 開啟 Vercel Authentication，讓預覽網址需要登入。

5. Deploy。完成後在 Settings → Domains 綁定正式網域（與 `APP_BASE_URL` 一致）。

### 5. 上線驗證（每一項都打勾才算完成）

1. 健康檢查（不帶金鑰只回 `{"ok":true}`）：

   ```bash
   curl -H "Authorization: Bearer <CRON_SECRET>" https://正式網址/api/health
   ```

   `checks` 內除了 `notify_recipients_set`（第 3 步才設定）以外都應為 `true`，`region` 為 `hnd1`。若 `schema_up_to_date` 為 `false`，回到第 2 步執行 migrate。
2. 用店長帳號登入 → 「醫師班表」補上週五醫師姓名、確認班表；「項目與營業」確認營業時間、填**通知收件地址**。
3. 「帳號與權限」建立各業務帳號（與代理店長帳號，平常保持停用）。
4. 以業務帳號建立一筆測試預約 → 取消它 → 收件信箱應收到「業務取消預約」即時信；後台「通知」頁顯示「已寄出」。
5. 手動觸發一次每日排程（台北 21:00 前執行只會回 `too_early`，屬正常）：

   ```bash
   curl -H "Authorization: Bearer <CRON_SECRET>" https://正式網址/api/cron/daily
   ```

6. Vercel → Settings → Cron Jobs 確認排程已啟用；隔天 21:00 後確認有收到日報（當天有「日報」事件時）。
7. 「操作紀錄」查得到上述操作。
8. 照「三、備份」做第一次離線備份，並照「四、還原 → 還原演練」確認備份可以用。

## 二、日常維運

### 系統會自動做的事

| 時間 | 內容 |
| --- | --- |
| 每次異動後 | 寄出設定為「即時」的通知信；失敗會在 1、5、30、120、720 分鐘後重試（最多 6 次） |
| 每天 21:00–21:59 | 寄出日報；順便補寄到期的重試 |
| 每天（Supabase Pro） | 資料庫自動備份 |

### 定期檢查（建議每週）

- 後台「通知」頁：有沒有紅字「寄送失敗」。修正原因後按「重新寄送」。
  - 「未設定通知收件地址」→ 項目與營業 → 通知設定
  - 「Resend 401/403」→ API key 失效或寄信網域驗證掉了
  - 「尚未設定寄信」→ Vercel 少了 `RESEND_API_KEY` 或 `NOTIFY_FROM`
- `/api/health`（帶金鑰）全部為 `true`。
- 錯誤紀錄：Vercel → 專案 → Logs，篩選 Error。

### 人員異動

- 業務離職：帳號與權限 → 先「轉出未來預約」給其他業務 → 再停用帳號（停用會立即登出）。
- 店長請假：啟用代理店長帳號；回來後停用。代理店長的每個操作都會即時通知店長。
- 建議至少建立**兩位店長帳號**（例如店長與負責人），避免唯一的店長忘記密碼時無人能重設。
- 忘記密碼：店長在「帳號與權限」重設。店長本人忘記密碼且沒有其他店長時，請工程人員協助（無法再用 `db:create-admin`，因為已有店長）。

### 更新程式

1. 有新的資料表變更（`supabase/migrations/` 有新檔案）時，**先**在電腦上對正式資料庫執行 `npm run db:migrate`，**再**部署程式。migration 只會新增欄位或資料表，舊版程式仍可正常運作。
2. 推送到正式分支後 Vercel 自動部署；部署完確認 `/api/health`。
3. 新版本有問題：Vercel → Deployments → 前一個版本 → **Instant Rollback**（只回復程式，不動資料）。

### 金鑰更換

| 金鑰 | 更換方式 |
| --- | --- |
| `CRON_SECRET` | 產生新值 → 更新 Vercel 環境變數 → Redeploy |
| `RESEND_API_KEY` | Resend 建新 key → 更新 Vercel → Redeploy → 刪除舊 key |
| 資料庫密碼 | Supabase 重設密碼 → 更新 Vercel 的 `DATABASE_URL` → Redeploy（重設到部署完成之間系統無法連線，請選離峰時間） |

## 三、備份

資料庫內有客戶姓名、電話、照護備註，**所有備份檔都必須加密，並與密碼分開保管**。

### 第一層：Supabase 自動備份（Pro 方案）

- 每天自動備份，保留期間依方案（Pro 為 7 天）。在 Supabase → Database → Backups 可看到清單。
- 需要回到「任意時間點」（例如精確回到誤操作前一分鐘）可另外加購 Point-in-Time Recovery。

### 第二層：離線加密備份（建議每月一次，以及每次重大更新前）

自動備份與正式資料在同一家服務；若 Supabase 帳號出問題，需要另一份自己保管的備份。

```bash
BACKUP_DATABASE_URL="<Session pooler 連線字串>" npm run db:backup
```

- 會要求輸入兩次**加密密碼**；產生 `backups/purein-日期時間.sql.gz.gpg`，並顯示檔案的 SHA-256。
- 檔案已用 AES-256 加密，沒有密碼無法讀取。`backups/` 已排除在 git 之外，**不要**上傳到 GitHub 或寄 email。
- 建議保存：最近 12 個月每月一份，存在診所指定的加密隨身碟或雲端硬碟（兩處）。
- 加密密碼存在診所的密碼管理工具，至少兩人知道。密碼遺失＝備份作廢。
- 在備份紀錄表記下日期、檔名、SHA-256、執行人。

## 四、還原

先判斷是哪一種情況：

### A. 少量資料被改錯或取消錯

**不要整份還原**（會把之後所有人的新預約一起蓋掉）。

1. 後台「操作紀錄」用預約編號或客戶姓名搜尋，看誰在何時改了什麼、原本的值是什麼。
2. 由店長在後台把資料改回來（改期、修改、重新建立預約）。
3. 若後台看不出原值，請工程人員把最近的備份還原到**本機或新的 Supabase 專案**（見 C 的指令）查詢原始資料，再由店長在後台修正。

### B. 整個資料庫損壞或大量資料被誤刪

1. 先暫停使用：通知業務暫停操作，並記下發生時間。
2. Supabase → Database → Backups，選擇損壞前最近的一份 → Restore。
   - 還原期間系統無法使用；備份時間之後的所有異動會消失，需依通知信、日報與紙本紀錄補登。
   - 有 Point-in-Time Recovery 時可選到損壞前的確切時間。
3. 還原後：`/api/health` 確認正常 → 店長登入抽查當天預約 → 通知業務恢復使用 → 補登遺失的預約。

### C. Supabase 專案無法使用（帳號遺失、專案被刪）

用第二層的離線備份還原到**新的** Supabase 專案：

1. 照「一、1」建立新專案（東京區）。
2. 在電腦上還原（目標必須是全新、空的資料庫，否則會拒絕）：

   ```bash
   RESTORE_DATABASE_URL="<新專案的 Session pooler 連線字串>" npm run db:restore -- backups/purein-日期時間.sql.gz.gpg
   ```

   - 輸入加密密碼；整份在一個交易內完成，失敗不會留下半套資料。
   - 完成後會重新鎖上資料表權限，並列出各表筆數，請與備份紀錄核對。
3. 對新資料庫執行 `npm run db:migrate`（備份之後若有新的 migration 會補上；沒有則顯示「已是最新」）。
4. Vercel 把 `DATABASE_URL` 換成新專案的 Transaction pooler 連線字串 → Redeploy → `/api/health` 確認。
5. 備份時間之後的異動需人工補登；所有人需重新登入的情況屬正常。

### 還原演練（建議每季一次，以及第一次備份後）

確認備份檔真的能用，不影響正式環境：

```bash
createdb purein_restore_test
```

```bash
RESTORE_DATABASE_URL="postgres://localhost/purein_restore_test" npm run db:restore -- backups/最新的備份檔
```

確認列出的筆數合理後刪除測試資料庫（內有個資，不要留著）：

```bash
dropdb purein_restore_test
```

## 附錄：環境變數總表

| 變數 | 用途 | 正式環境 |
| --- | --- | --- |
| `DATABASE_URL` | 程式連資料庫（Transaction pooler 6543） | 必填 |
| `DATABASE_POOL_MAX` | 每個程式實例的連線數上限，預設 5 | 選填 |
| `RESEND_API_KEY`、`NOTIFY_FROM` | 寄通知信；未設定時不寄，通知頁顯示原因 | 必填 |
| `APP_BASE_URL` | 信中「到後台查看」的連結 | 建議 |
| `CRON_SECRET` | 每日排程與 `/api/health` 詳細資訊的金鑰；未設定時排程端點拒絕執行 | 必填 |
| `DEV_PASSWORD` | 開發用測試帳號密碼（正式環境不使用） | 不填 |
| `BACKUP_DATABASE_URL`、`RESTORE_DATABASE_URL` | 只在電腦上執行備份／還原時使用，不要設在 Vercel | 不填 |
